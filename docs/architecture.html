餐廳點餐系統架構說明

這份文件用比較接近 C++ client/server 的角度，說明為什麼專案會拆成 Nuxt 前端、NestJS API 後端，以及未來 PostgreSQL 資料庫。

先講結論

apps/web-nuxt

這是前端程式。它負責畫面、按鈕、表單、購物車狀態、頁面切換，以及呼叫後端 API。

apps/api

這是後端程式。它負責商業規則、訂單狀態、權限、交易、資料庫存取，以及避免資料被前端亂改。

PostgreSQL

這是正式資料庫。它負責保存菜單、桌號、訂單、庫存、稽核紀錄，並提供交易一致性。

為什麼不是全部寫在同一個 App？

對前端新手來說，最直覺的想法是把畫面、資料、訂單邏輯都寫在一個地方。但餐廳點餐系統有一個很重要的差異： 畫面可以暫時壞掉，但訂單資料不能亂掉。

前端跑在客人的手機或店員平板上，使用者可以重整、斷線、連點，甚至送出重複請求。因此正式版本不能相信前端自己說「這筆訂單成立」。 真正能決定訂單成立、庫存是否可用、狀態能不能轉換的地方，應該是後端 API。

用 C++ 比喻：web-nuxt 像 GUI client，api 像 authoritative server。 Client 負責互動體驗，Server 負責可信任的狀態轉移。

一次點餐的資料流

客人掃 QR Code
Nuxt 顯示菜單
客人加入購物車
Nuxt 呼叫 API
API 寫入 PostgreSQL

目前 MVP 還沒有真的接資料庫，菜單資料先放在 apps/web-nuxt/data/menu.ts。 等流程確認後，這些資料會改由 apps/api 提供，Nuxt 再用 HTTP request 讀取。

Next.js、React、Vue、Nuxt 的關係

名稱 它是什麼 本專案決策
React 前端 UI library。 不採用。
Next.js React 生態的全功能框架。 已移除。
Vue 前端 UI framework。 採用。
Nuxt Vue 生態中接近 Next.js 定位的全功能框架。 採用，放在 apps/web-nuxt。

為什麼 API 用 NestJS？

NestJS 是 TypeScript 後端框架。它的架構很像比較嚴謹的 server application：有 module、controller、service、dependency injection。 對商用系統來說，這比把所有 API handler 隨手散在前端框架裡更適合長期維護。

層級 責任 之後會放什麼
Controller 接 HTTP request，回 HTTP response。 POST /api/orders、PATCH /api/menu-items/:id/availability
Service 商業邏輯。 訂單狀態機、庫存檢查、權限判斷。
Repository / ORM 資料庫存取。 PostgreSQL queries、transactions、migrations。

為什麼正式資料庫選 PostgreSQL？

SQLite 很適合本機 demo 或單機工具，但餐廳現場會有多台手機或平板同時操作。 只要牽涉訂單、取消、庫存與日結，就需要穩定的 transaction、constraint、locking 和備份策略。

SQLite 不是不能用，而是不適合作為這套系統的正式主資料庫。它可以留給測試、本機 demo，或未來離線 local cache。

目前檔案怎麼讀

路徑 用途
apps/web-nuxt/app.vue 目前前端入口，放頁面狀態、購物車、庫存展示狀態。
apps/web-nuxt/components/ 畫面元件，例如菜單、餐點詳情、店員控制台、購物車。
apps/web-nuxt/data/menu.ts 暫時的假資料，未來會被 API 取代。
apps/api/src/routes/ 目前 API endpoint 起點。
docs/adr/ 技術決策紀錄，例如技術棧與資料庫選型。

接下來會怎麼長大

目前前端還是用本機假資料。下一階段會讓 Nuxt 從 NestJS API 讀資料，再讓 NestJS 接 PostgreSQL。 到那一步後，前端只負責「送出使用者意圖」，後端才負責「判斷這件事是否能成立」。
